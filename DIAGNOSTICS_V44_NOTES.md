# GET Mobile v44 — Diagnostics (read / clear fault codes, ECM + TCM)

New home tile: **Diagnostics**. Pick ECM or TCM, tap Read Codes / Clear Codes.
Each code shows its code, description, ACTIVE/STORED/PENDING/HISTORY badge, a
MIL badge if the warning light is requested, the raw 24-bit value, and the
decoded status flags. A share button exports a plain-text report.

## What's ported from VW_Flash (bri3d/VW_Flash, BSD-2-Clause)
* `get_dtcs`: extended diagnostic session (0x10 03), then ReadDTCInformation
  0x19 sub-function 0x02. Default status mask **0xAB** (same as VW_Flash);
  the "Include pending codes" toggle uses 0xAF.
* `data/dtcs.csv` bundled as `Diagnostics/Data/simos18_ecm_dtcs.csv`
  (657 Simos18 ECM codes), matched on the exact 24-bit DTC value like
  `dtc_handler.dtcs_to_human`.
* Clearing: VW_Flash's `send_obd(0x04)` on functional address 0x700.
* Module addressing: ECM 0x7E0/0x7E8, TCM 0x7E1/0x7E9 (DQ250-MQB and DQ381-MQB).

## Deliberate differences from VW_Flash
* **Unmatched codes are shown, not dropped.** VW_Flash silently omits any DTC
  missing from its table; here it appears with its raw value.
* **Clear tries UDS 0x14 (group 0xFFFFFF) first**, per module, because OBD
  Mode 04 only clears emissions DTCs and can't be aimed at the TCM. If the
  module refuses, it falls back to VW_Flash's Mode 04 method. The module is
  re-read afterwards so the screen shows what is actually left.

## TCM descriptions — read this
VW_Flash has **no TCM description table**. For the TCM the app decodes the
3-byte code with the standard SAE J2012 bit layout (0x173500 -> P1735-00) and
looks it up in `sae_generic_dtcs.csv` (167 generic transmission/network codes,
generated by script, plus P1735/P1736 as reported for the DQ381). That is only
correct if the DSG reports SAE-format codes. If it reports VW-internal numbers
(as the Simos18 ECM does), the decoded code won't match anything and the card
shows the raw hex/decimal with "No description available" — it will not invent
one. Each description is tagged with its source ("Simos18 table" / "SAE
generic") so you can see how much to trust it.
**Please read the TCM once on the car and send me the raw values** (use the
Share button); if they're internal numbers we can add a proper DSG table.

## Transport changes
* `UdsPdu`/`UdsClient`: added ClearDiagnosticInformation (0x14).
* ELM327 (WiFi + BLE): headers now follow each request's CAN IDs
  (ATSH/ATCRA), otherwise a "TCM" request would silently be answered by the
  ECM. Response parser now also recognises 0x59 / 0x54 / 0x44. Gauge traffic
  (7E0/7E8) is unchanged. ELM327 remains untested against real hardware.
* GVRET WiFi and the BLE bridge already honoured per-request IDs; no changes.

## Untested
Not compiled or run against a car (no Swift toolchain / hardware here). Checked:
all touched files parse with a Swift grammar; CSV parsing, SAE decode and DTC
payload parsing were mirrored in Python and match Python's `csv` module and
VW_Flash's mask/lookup behaviour. Expect possibly one small CI compile fix.
Notes from VW_Flash issue #191: an ECU in the unlocked (X13) state returned
NRC 0x11 to ReadDTCInformation; the app reports that in plain words.

## Side observation (not changed)
HSL/Standard logger screens release the ECU-ownership lock only via their
**Done** button. Leaving with the back arrow appears to leave `isHslActive`
true, which would make Gauges > Start Live silently do nothing until Done is
used. Diagnostics releases it in `onDisappear`, so it doesn't have this issue.

# v45 — HSL fix, bigger home tiles, bigger logo

## HSL timing out again — likely cause found and fixed
`DiagnosticsSession` (v44) switches the ECM/TCM to the **extended diagnostic
session** (`0x10 03`) before reading/clearing codes, and never switched it
back. That's the same session state your earlier HSL debugging specifically
flagged as troublesome on this ECU (extended session + seed-key unlock
producing a real NRC). HSL never touches session state itself - it assumes
default and layers its own 0x3E service on top - so if you opened Diagnostics
and tapped Read/Clear on the ECM, then went to HSL shortly after (inside the
ECU's ~5s S3 timer, before it would auto-revert on its own), HSL would be
talking to a module sitting in a session it doesn't expect. That lines up with
"timing out like it used to."

Fix: `DiagnosticsSession.read()`/`.clear()` now unconditionally send the
module back to the default session (`0x10 01`) before releasing it, on every
exit path including errors - not just on success.

**This is my best-supported theory, not a confirmed fix** - same caveat as
the v43 chart fix. If HSL still times out after this, it isn't the session
issue; a device crash/connection log from the moment HSL fails to start would
let me pin it down instead of guessing again. One thing worth telling me
either way: did you open Diagnostics (and tap Read or Clear) before HSL
failed, or did HSL fail on a fresh connect with Diagnostics untouched? That
alone would confirm or rule this theory out.
